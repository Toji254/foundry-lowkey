# Lowkey Research Scout — 2026-11-26

Checked: 26 November 2026. Public-web research only. No third-party systems were tested.

## 1. Three unrelated ideas

### Idea 1 — Dustline: Dormant-Market Cliff Tester

**Everyday example:** A lending market looks nearly empty. Its interest calculation divides by the tiny amount left in the market, so a small state change can make the index jump absurdly.

**Problem / user:** Lending-protocol engineers and risk curators need a reproducible test for dangerous *near-zero-but-not-zero* accounting states—not just a dashboard showing low utilization.

**Evidence:** The Block reported Kava Lend's dormant BUSD market was manipulated to a tiny net-supply denominator, multiplying its index roughly 243,000× before 127 KAVA borrow operations. Bitquery's block-by-block analysis independently describes the denominator being reduced to two base units and the index amplification. Kava said the incident was contained to Kava Lend; its official post-mortem was not available in The Block's report. Treat the incident mechanics as reported/on-chain analysis, not a protocol-authored root-cause report.

Sources:
- https://www.theblock.co/news/defi/2026-11-14-kava-lend-loses-roughly-3-8-million-to-hack-sending-kava-token-down-nearly-40
- https://www.bitquery.io/investigations/kava-hack

**Closest products / prior art (checked today):**

| Product | What it already does | Gap vs. Dustline |
|---|---|---|
| [Chaos Labs risk stewards](https://governance.aave.com/t/arfc-chaos-labs-risk-stewards-decrease-supply-and-borrow-caps-on-aave-v3-03-25-25/21563) | Monitors under-utilized markets and recommends caps/deprecation. | Strong overlap in identifying low-activity markets; no documented automated denominator-boundary test in this proposal. |
| [Gauntlet Aave dashboards](https://governance.aave.com/t/gauntlet-analytics-dashboard-for-the-aave-community/9980) | Tracks usage, asset metrics, concentration, liquidations and simulations. | Analytics and risk recommendations, not the proposed source/state boundary-test generator. |
| [LlamaRisk Market Health Scores](https://llamarisk.com/research/curve-market-health-methodology) | Quantitative market-health scoring: collateral, liquidity, liquidation, concentration and market mechanics. | Broad health coverage; no specific near-zero denominator stress test documented. |
| [DeFiLlama Risk Curators](https://defillama.com/pro/risk-curators-5jg1yr) | Tracks curator firms, vault-management/risk activity and market metrics. | Market oversight already has an established ecosystem; not a source-level stress-test generator. |
| [Tenderly Simulator](https://tenderly.co/products/simulator) | Forked-state transaction simulation, dependent bundles, Virtual Environments and monitoring. | The execution engine is already available; the proposed value is generating the boundary cases and invariants automatically. |

**Overlap test:** Market monitoring, utilization/cap recommendations and transaction simulation are already solved or heavily covered. Automatic tests around net-supply denominators, reserve offsets, dust transitions and repeated accrual are *not documented in the inspected feature pages*—absence from docs is not proof they are unsupported.

**Simple MVP:**
1. Use a synthetic lending pool and a locally pinned state fixture only.
2. Identify a candidate denominator/index formula and generate boundary values (zero, one/two base units, tiny positive, reserve-over-cash, just-above guard).
3. Generate a bounded local property test: index growth must stay within an explicit protocol-defined bound and never silently amplify beyond it.
4. Emit a minimal failing state and replay seed; do not call a live RPC by default.

**Established vs. novel:** Property testing, arithmetic analysis and local EVM simulation are established. The novel hypothesis is a dedicated market-lifecycle/near-zero-denominator case generator that links code-derived arithmetic to market state. It is not a generic “AI risk dashboard.”

**Threat model / hardest assumption:** An attacker can reach a state with a tiny positive denominator through permitted market actions. The hardest part is deriving the correct denominator and expected invariant across different lending designs without false alarms.

**Cheap falsification experiment:** Build two synthetic index models—unsafe and guarded—then run 50 deterministic boundary sequences. If the generator cannot reliably expose the unsafe case while preserving zero findings on controls, or a major risk platform already provides this exact workflow, drop it.

**Potential value:** Catch catastrophic accounting amplification before asset listing, migration or market sunset.

**First user to test with:** A lending-protocol risk engineer who owns collateral onboarding/sunset decisions.

**Novelty confidence:** Low–medium. The problem is real; the tool gap is not proven. A large risk-curator can add this feature.

**Verdict:** **Investigate further; do not build a standalone business yet.** It could be a focused Lowkey test-generation capability if a small prototype demonstrates incremental coverage.

**Independence check:** Lending-market state arithmetic and risk operations; unrelated to bridge-message testing or validator networking.

### Idea 2 — MessageShuffle: Cross-Chain Delivery Schedule Mutator

**Everyday example:** A bridge sends a message. The relayer retries it, the destination receives a duplicate, a timeout fires, and the original message arrives late. Does the application pay twice, refund too early, or accept the wrong order?

**Problem / user:** Bridge and cross-chain application engineers repeatedly hand-write failure cases. They need deterministic, replayable schedules for duplicate delivery, delay, reorder, timeout, destination failure and refund boundaries.

**Evidence:** The Block reports Chainflip's September 2026 Tron memo-processing exploit double-processed six withdrawals. This demonstrates a real duplicate-processing failure, but the current November vault incident is a different key/network compromise and must not be conflated with it.

Source:
- https://www.theblock.co/news/defi/2026-11-21-chainflips-flip-drops-34-after-attacker-drains-4-86-million-from-vault-with-suspected-key-compromise

**Closest products / prior art (checked today):**

| Tool / product | What it already does | Overlap / limitation |
|---|---|---|
| [Chainlink Local CCIP](https://docs.chain.link/chainlink-local/learn/ccip-v2-local) | Local/fork simulator, routing, message outcomes/status, pending/manual execution. API includes message status and manual execution. | Strong local simulator; schedule mutation is not documented in inspected docs. |
| [LayerZero Devtools](https://github.com/LayerZero-Labs/devtools/blob/main/DEVELOPMENT.md) | Local development/test environments and test projects for LayerZero apps. | Bridge-specific local tests already exist; developers author their scenarios. |
| [Hyperlane local E2E](https://github.com/hyperlane-xyz/hyperlane-monorepo/blob/main/rust/README.md) | Builds/deploys contracts and starts local node, relayer and validator for end-to-end tests. | Existing integration harness; no general delivery-schedule compiler found in the inspected README. |
| [Cosmos interchaintest](https://github.com/cosmos/interchaintest) | Generic IBC integration and conformance test harnesses for repeatable chain-level scenarios, including connections, channels, relaying, acknowledgements and timeouts; setup/resource cost was not measured here. | Mature custom/conformance test harness; not lightweight for an 8 GB laptop. |
| [ChainScore Labs bridge testing](https://chainscorelabs.com/services/developer-tooling/local-blockchain-networks-and-testnets/cross-chain-bridge-integration-testing-platform) | Claims mock bridges, 15+ chains, 500+ attack vectors, 24/7 fuzzing and automated regression testing; its page also claims 1,000+ preconfigured scenarios and gives prices. | Direct commercial overlap. Claims are marketing; I found no public demo/repository or independent benchmark to verify them, and the page's 500 vs 1,000 scenario claims are inconsistent. |
| [XIR research](https://github.com/lysrain21/XIR) | A cross-protocol message-verification framework/IR; repo describes Hyperlane and LayerZero V2 integrations. Published campaign reports 13 cases across two routes and 30 repeats (780 runs). | Closest research prior art for adversarial cross-chain message composition; research implementation, not independently reproduced here. |

**Feature overlap test:**
- Local chain/message simulation — **already solved**.
- Reorg, timeout, retry and failure testing — **partially solved** by existing stacks and services.
- Automatically compiling a user-specified *delivery timeline/property* into bounded permutations and a minimized replay seed — **not observed in the inspected docs**, but ChainScore's direct claims and XIR mean this is not a clean market gap.

**Simple MVP:** A protocol-neutral message timeline model (source send → relay → destination execute → acknowledgement/refund), a synthetic bridge adapter, and a bounded generator for duplicates, delays, reordering, timeout/late delivery, destination revert and retry. Output a reproducible counterexample timeline plus paired control. Add an existing local simulator adapter only if the first experiment proves value.

**Established vs. novel:** Stateful testing and local-chain adapters are established. The new hypothesis is a small, adapter-independent schedule compiler that tests exactly-once/ordering/refund properties instead of another bridge simulator.

**Threat model / hardest assumption:** A test schedule can accurately represent the target protocol's finality, message identity and retry semantics. The hardest risk is false confidence from an abstract model that differs from the real bridge.

**Cheap falsification experiment:** 50 deterministic schedules against an intentionally buggy synthetic bridge and a safe control; compare generated failures with hand-authored tests and the capabilities of existing local frameworks. If it adds no distinct counterexample, reject.

**Potential value:** Better cross-chain regression tests without maintaining a separate bespoke chaos harness for each scenario.

**First user to test with:** A bridge integration/QA engineer.

**Novelty confidence:** Low. Existing frameworks and a claimed commercial service cover much of the outcome.

**Verdict:** **Reject as a standalone product.** Revisit only as a Lowkey adapter/feature if the tiny experiment proves an uncovered scenario.

**Independence check:** Bridge message delivery and settlement semantics; not lending-accounting risk or node peer authorization.

### Idea 3 — PeerPrivilege Atlas: Stateful P2P Admission Contract

**Everyday example:** A validator is registered but not yet active. The protocol allows it to connect to active validators so it can eventually join. What messages and handlers can that inactive peer reach during that window?

**Problem / user:** Blockchain client maintainers and node-security reviewers need a way to test the *state-to-peer privilege boundary* (registered, pending, active, jailed, removed), not just scan dependencies or watch validator uptime.

**Evidence:** Chainflip's official Part 1 incident report (23 Nov 2026) says the attacker registered with minimum stake, never entered the active validator set, but registration still permitted P2P connections to active validators. Chainflip says those connections were used to exploit a memory-safety flaw in a third-party networking library and extract key shares. Some steps are explicitly still under investigation; the library is unnamed.

Source:
- https://chainflip.io/blog/incident-report-vault-exploit-21-november-2026-part-1

**Closest products / prior art (checked today):**

| Tool | What it already does | Gap vs. idea |
|---|---|---|
| [Semgrep](https://github.com/semgrep/semgrep) | Pattern/semantic SAST across Rust, Go and many languages; local scanning and CI. | Generic code rules; no documented validator lifecycle-to-handler permission model. |
| [CodeQL Rust dataflow](https://codeql.github.com/docs/codeql-language-guides/analyzing-data-flow-in-rust/) | AST/dataflow libraries, local/global flow and taint tracking; custom query capability. | Can be extended, but the proposed peer-state invariants are not a built-in product workflow. |
| [cargo-fuzz](https://github.com/rust-fuzz/cargo-fuzz) | libFuzzer targets, input mutation, minimization and coverage. | Requires a fuzz target/harness; doesn't infer protocol admission states automatically. |
| [cargo-audit](https://github.com/rustsec/rustsec/tree/main/cargo-audit) | Dependency vulnerability auditing against RustSec advisories. | Dependency risk, not peer lifecycle authorization. |
| [Telcoin tn-p2p-allow-sync](https://github.com/Telcoin-Association/tn-p2p-allow-sync) | Applies a node-reported eligible peer set to host firewall rules; a runtime network-layer allowlist. | Prevents unwanted network connections at the firewall, but is not a source-code audit of handler permissions. |
| [P2P.org validator monitoring](https://p2p.org/economy/validator-monitoring-service-user-guide/) | Validator performance, participation metrics, alerts and dashboards. | Operational monitoring, not stateful handler access analysis. |

**Overlap test:** SAST, dependency auditing, fuzzing, firewall allowlists and validator uptime are all existing capabilities. The searched gap is an explicit, reviewable **peer lifecycle state → allowed handler/message capability** contract with generated transition tests. I did not find a direct product for that exact workflow; search scope is limited and that is not proof of absence.

**Simple MVP:**
1. A small TOML/YAML policy declares peer states and the handlers/messages allowed in each state.
2. Map a handful of real peer entry points to those declarations (initially manual annotations).
3. Generate deterministic state-transition tests for register → connect → activate → jail → reconnect → remove.
4. Fail CI only on a concrete policy mismatch; keep static-analysis matches as leads.

**How we'd build:** A state graph and capability matrix, then bounded model-based test generation against a local synthetic node. Static analysis is used to map gates; no live peers, RPC probes or network testing.

**Established vs. novel:** State-machine testing, SAST and fuzzing are established. The novel hypothesis is a typed peer-capability contract and state-transition generator for blockchain validator P2P code.

**Threat model / hardest assumption:** An attacker is an untrusted peer in a non-active lifecycle state. The hard part is deciding which pre-activation connections are legitimately required for discovery/bootstrap, and whether handler gating can be inferred without drowning maintainers in false positives.

**Cheap falsification experiment:** 20 synthetic Rust peer handlers (allowed/forbidden across lifecycle states), with deliberate ungated handlers and safe controls. Compare findings against a custom Semgrep/CodeQL rule. Measure false positives and whether the report identifies the state mismatch, not merely a suspicious call.

**Potential value:** A reviewable admission boundary and reproducible tests for a class of node-level exposure that smart-contract-only auditors often miss.

**First user to test with:** A Rust/Go blockchain client or validator-network maintainer.

**Novelty confidence:** Medium–low. No direct product surfaced, but the mechanism is an extension of existing SAST/model-based testing and user demand is unverified.

**Verdict:** **Investigate further.** This is the most interesting candidate today, but validate the model and maintainer demand before building.

**Independence check:** Validator-network peer admission; separate from lending arithmetic and cross-chain message delivery.

### Original vulnerability hunt

**Target:** Lowkey lk-test-drive, starting SHA above. Source-reviewed code path only; no local Lowkey reproduction.

**Hypothesis:** In _source_context, an untrusted workspace file may be swapped between path.is_symlink()/path.stat() and the later path.open(), causing a bounded source read from outside the intended workspace.

**Synthetic experiment:** A controlled temporary-file test reproduced the generic race:
- Check → stat → swap leaf to an external symlink → path-open read: OUTSIDE_FIXTURE_ONLY.
- Open with O_NOFOLLOW → fstat → swap leaf → read from the held descriptor: SAFE_FIXTURE_FD.

This confirms the generic mechanism, not Lowkey runtime behavior. A first attempted mitigation that merely saved a canonical path string still followed the swapped leaf; it was rejected. The descriptor-based check/read protected the synthetic leaf swap. Parent-component races remain.

**Prerequisites and impact:** A concurrent actor must be able to mutate the scanned workspace during context collection. The source excerpt limit is bounded, but an unintended local read could enter context and, if the user has explicitly enabled an external provider and invokes that path, be exposed outside the machine. No provider call or external target interaction occurred.

**Prior-art search:** No Lowkey issue surfaced in searches for the candidate. The class is well-known: https://github.com/BurntSushi/walkdir/issues/209 and https://github.com/Quartio-Studio/yulius/issues/744 describe check/open symlink races; Yulius reports a descriptor-based fix and race tests. This is a Lowkey-specific source-reviewed candidate, not a novel vulnerability class and not confirmed in runtime.

**Next test:** implement descriptor-based reads in the local checkout; add deterministic leaf and parent swap tests, then run focused and full suites.
