## Three unrelated ideas

### 1) Roundoff Envelope — investigate further (incremental / medium-low novelty)

**Everyday example:** a single calculation loses only a tiny fraction of a cent, but repeated calls may quietly favor one side until the protocol's accounting drifts.

**Problem/user:** DeFi math engineers and auditors want to know not only *where* integer division rounds, but the cumulative directional error and the sequence/state conditions that amplify it.

**Evidence:** OpenZeppelin explains ERC-4626 rounding and the empty-vault inflation attack; its 2025 security rewind describes zkLend's rounding-down exploit. A September 2025 TruStakePOL review flags a withdrawal rounding direction that favors withdrawing users. These are real recurring classes, not proof of demand for a new product.
- OpenZeppelin ERC-4626: https://docs.openzeppelin.com/contracts/5.x/erc4626
- OpenZeppelin 2025 rewind: https://www.openzeppelin.com/news/web3-security-auditors-2025-rewind
- TruStakePOL audit report: https://www.trufin.io/audits/TruPOL-Nethermind-audit-september-2025.pdf

**MVP:** For one selected arithmetic-heavy function, extract/annotate conversion sites; run bounded stateful sequences against an independent high-precision integer/rational model; calculate per-step remainder, directional bias, accumulated drift, and amplification near boundary values; report minimized sequences and a control. No automatic vulnerability verdict.

**Market/prior-art matrix**
| Product/tool | Existing capability | Overlap / remaining gap |
|---|---|---|
| [Slither](https://github.com/crytic/slither) | Static detectors, including divide-before-multiply; custom analyses | Flags code patterns; no quantified sequence-level error budget documented in inspected docs |
| [Echidna](https://github.com/crytic/echidna) | Stateful ABI fuzzing against user invariants; minimization/coverage | Can find drift when the auditor supplies a suitable invariant; does not automatically produce a numerical rounding envelope |
| [Certora Prover](https://www.certora.com/) | Formal verification of developer-specified properties | Strong overlap for proving properties; requires a specification, and the proposed error-budget visualization is not established as a built-in feature |
| [OpenZeppelin ERC-4626](https://docs.openzeppelin.com/contracts/5.x/erc4626) | Standard rounding directions and virtual-offset defense guidance | Solves/mitigates known vault-specific risks; not a general drift profiler |
| [Foundry](https://book.getfoundry.sh/forge/invariant-testing) | Stateful invariant testing | Custom test harness can cover the same problem; no tool replacement claim |
| [Firepan](https://firepan.com/vulnerabilities/precision-loss/) | Precision-loss review guidance/detection for arithmetic patterns | Direct overlap on precision-loss review; a cumulative error envelope was not documented on the inspected page |
| [OpenSentry](https://opensentry.tech/) | User-facing contract risk analysis, including precision-loss concerns | Direct overlap on detecting/reporting precision loss; no quantified multi-call envelope observed in inspected description |

**Overlap test:** static rounding patterns are already covered; fuzzing/formal tools can discover violations with a custom property. The proposed difference is a *measured, per-path error budget and sensitivity envelope*, not another rounding detector. An incumbent could add it, so the gap is incremental and not defensible yet.

**Hardest risk:** the reference model may omit token behavior, unit changes, nonlinear economic effects, or the intended rounding policy. A measured arithmetic drift is not automatically exploitable.

**Cheap falsification:** synthetic share/reward accumulator; compare Solidity results with an exact rational reference over repeated deposits/withdrawals/claims; deliberately reverse one rounding direction and see whether the report quantifies and minimizes the drift without flagging a safe control.

**Potential value / first user:** faster math triage for an audit team; interview a protocol math engineer or contest auditor who has built custom rounding invariants. No interview or willingness-to-pay evidence collected.

**Independence check:** this is arithmetic/state-sequence analysis, not proof artifact integrity or RPC infrastructure reliability.

**Verdict:** investigate; do not build until an auditor confirms the output is useful beyond a custom Echidna/Foundry invariant.

### 2) Proof Lineage Gate — investigate, but overlap is high

**Everyday example:** the circuit source changed, but the release accidentally ships a proving key or verifier generated from an older circuit. A proof can still verify against a valid key—it may simply prove the wrong version of the intended statement.

**Problem/user:** ZK protocol release engineers want one offline CI check that ties source, compiler/config, constraint system, proving/verification keys, public-input schema, ceremony transcript, generated verifier, and deployed verifier code into one release lineage.

**Evidence:** existing teams already pin hashes, tool versions and ceremony transcripts. That demonstrates the integrity problem is recognized; it does not prove a new product is needed.
- zk-id reproducible builds: https://zk-id.io/docs/reproducible-builds/
- QuantZK artifact rotation runbook: https://quantzk.com/docs/circuit-artifact-rotation-runbook
- QuantZK manifest/pinning specification: https://quantzk.com/docs/vdi-spec
- [Circomkit](https://github.com/erhant/circomkit) compile/test/export tooling
- [SLSA artifact verification](https://slsa.dev/spec/v1.0/verifying-artifacts) and [Sigstore](https://docs.sigstore.dev/cosign/signing/overview/) general build provenance/signing

**MVP:** offline CI command for Circom/snarkjs: rebuild in a pinned container or environment; verify artifact hashes and ceremony transcript; validate the ordered public-input schema; compare generated verifier ABI/bytecode and deployed verifier address/code hash against the release manifest; produce a signed, machine-readable pass/fail report. Never deploy or send transactions.

**Market/prior-art matrix**
| Product/tool | Existing capability | Overlap / gap |
|---|---|---|
| [zk-id](https://zk-id.io/docs/reproducible-builds/) | Rebuild circuits; pin zkey/vkey hashes and toolchain; CI checks hashes | Direct overlap on reproducible artifact integrity |
| [QuantZK](https://quantzk.com/docs/circuit-artifact-rotation-runbook) | Manifest-pinned artifacts, rotation workflow, transcript and verifier registry pins | Direct overlap on artifact/version management |
| [Circomkit](https://github.com/erhant/circomkit) | Circuit compilation, witness/proof tests, verifier/calldata export | Covers testing and generated outputs; cross-release deployed-verifier lineage not established in inspected docs |
| [0gzk](https://github.com/0gzk/core) | Content-addressed circuit bundle (WASM, zkey, verification key, verifier, metadata), optional on-chain registry | Very close overlap on bundling and integrity; deployed-verifier/public-input-schema lineage is the only possible gap not established in inspected docs |
| [SLSA](https://slsa.dev/spec/v1.0/verifying-artifacts) | General build provenance verification | Provides a framework, not ZK-specific semantic consistency |
| [Sigstore](https://docs.sigstore.dev/cosign/signing/overview/) | Artifact signing and transparency | Establishes identity/integrity of signed artifacts, not whether all artifacts encode the same circuit |

**Overlap test:** hashes, reproducible builds, ceremony checks, and artifact rotation already exist. The possible gap is the *cross-layer semantic binding* through the public-input schema and deployed verifier. It is not proven missing—existing pipelines could implement it with a small script.

**Hardest risk:** a matching hash chain only proves identity and provenance of artifacts, not that the circuit is correct, the ceremony was honest, or the app interprets public inputs correctly.

**Cheap falsification:** swap a vkey, reorder public inputs, change a compiler flag, replace verifier bytecode, and alter a transcript pin; each must fail. A clean rebuild must pass. Test on a tiny toy circuit first.

**Potential value / first user:** fewer accidental mismatched ZK releases; interview a team shipping a circuit and verifier together. No demand evidence collected.

**Independence check:** this is cryptographic release supply-chain integrity, unrelated to DeFi accounting drift or RPC provider health.

**Verdict:** investigate only if a ZK team shows that existing manifests/check scripts miss a real release failure; otherwise reject as a thin wrapper.

### 3) RPC Workload Fingerprint — reject (crowded)

**Everyday example:** an RPC endpoint says “healthy,” but the exact method or history your indexer needs is rate-limited, pruned, capped, or inconsistent.

**Problem/user:** dApp/indexer operators need workload-specific RPC capability checks before selecting a provider. This is real operational friction, but the product space is already heavily covered.

**Evidence:** providers and aggregators expose method support, failover, health, capability qualification and consistency controls.
- [eRPC](https://erpc.cloud/) and [its source](https://github.com/erpc/erpc): upstream health, automatic method routing, consensus/integrity checks and per-provider observability
- [Direct consistency rules](https://direct.dev/rpc/docs/behind/keeping-data-consistent): shared reference block/hash for supported reads
- [Direct provider qualification](https://direct.dev/rpc/docs/behind/qualifying-providers): method/chain/state/history checks and capability requirements
- [OnFinality node alerts](https://documentation.onfinality.io/support/dedicated-node-alerts): sync and disk alerts
- [OnFinality infrastructure](https://www.onfinality.io/en): multi-network RPC and data services

**MVP (if ever):** a local, read-only probe profile for one app workload (pinned-block reads, archive depth, log range, trace method, WebSocket reconnect/reorg behavior, chain identity, latency/error limits). No transactions.

**Feature overlap:** liveness, method support, provider routing, multi-provider consistency and monitoring are already substantially solved. The only unverified gap is a portable user-defined “workload contract” report; that is too small and too easy for incumbents to add to justify a product.

**Hardest risk:** probes may be expensive or misrepresent a provider's limits; results are endpoint-, plan-, chain-, and time-specific. A probe should be bounded and read-only.

**Cheap validation:** compare a hand-written capability checklist against eRPC and Direct docs for one indexer workload; if it adds no uncovered decision, stop.

**Potential value / first user:** convenience for a solo indexer developer, but weak differentiation and no demand evidence.

**Independence check:** infrastructure compatibility/observability, not accounting math or ZK release integrity.

**Verdict:** reject as a standalone product.

## Original vulnerability hunt — LK-AI-SEC-001 (source-reviewed candidate, NOT reproduced)

**Target:** LowkeyCast `Toji254/foundry-lowkey`, `lk-test-drive` SHA `a9792028b99c8389546a83867c8f60030e142319`; current `integration-test-drive` SHA `2d6d11f7a7ded6442f0d9bfcbc9f06a8a9241378`.

**Code path:** `lowkey/ai_harness.py::_source_context`. Both branches use the same relevant pattern:
- reject files that are symlinks at enumeration time;
- separately call `path.stat()` to bound size;
- later open the same pathname with `path.open()`, which resolves it again.

Test-drive references: [symlink check line 1165](https://github.com/Toji254/foundry-lowkey/blob/a9792028b99c8389546a83867c8f60030e142319/lowkey/ai_harness.py#L1165), [size check line 1176](https://github.com/Toji254/foundry-lowkey/blob/a9792028b99c8389546a83867c8f60030e142319/lowkey/ai_harness.py#L1176), [read line 1205](https://github.com/Toji254/foundry-lowkey/blob/a9792028b99c8389546a83867c8f60030e142319/lowkey/ai_harness.py#L1205).
Integration references: [symlink check line 1337](https://github.com/Toji254/foundry-lowkey/blob/2d6d11f7a7ded6442f0d9bfcbc9f06a8a9241378/lowkey/ai_harness.py#L1337), [size check line 1348](https://github.com/Toji254/foundry-lowkey/blob/2d6d11f7a7ded6442f0d9bfcbc9f06a8a9241378/lowkey/ai_harness.py#L1348), [read line 1377](https://github.com/Toji254/foundry-lowkey/blob/2d6d11f7a7ded6442f0d9bfcbc9f06a8a9241378/lowkey/ai_harness.py#L1377).

**Hypothesis:** a process able to mutate the selected workspace concurrently could replace a source file (or parent path) between check and read. The collector may then read outside the project root. If the user has explicitly enabled an external AI review, the bounded excerpt could leave the machine. This is conditional on a local race and the AI-review path; the normal static-symlink case is filtered, and obvious secrets are redacted. Severity is not assigned without reproduction.

**Disconfirming checks:** source review found no resolved-path containment check or no-follow file descriptor on this path. The test `test_source_context_excludes_tests_dependencies_and_symlinks_but_includes_deploy_scripts` only covers a static symlink, not replacement during the check/read window. A safe reader elsewhere in the repository would not prove this code path safe.

**Mitigation design:** hold a safe file descriptor from the project root; traverse components without following symlinks (dirfd-based, no-follow; use an OS-specific atomic beneath/no-symlink primitive where available); validate the opened inode with `fstat`; apply the size limit to that fd; read from the fd, never reopen the original path. Fail closed on unsupported secure traversal. Add tests for static symlink, swapped final file, swapped parent directory, oversized file, and benign internal file. A fake provider must prove no external request is made when the reader rejects the path.

**Prior-art screen:** this is a known TOCTOU/symlink class, not a novelty claim. [Claude Code GHSA (Oct 5, 2026)](https://github.com/anthropics/claude-code/security/advisories/GHSA-5j29-h97v-84ch) and [MCP filesystem server GHSA](https://github.com/modelcontextprotocol/servers/security/advisories/GHSA-53mr-w429-c597) show related check/use races in agent file tools. The Lowkey-specific candidate has not been locally reproduced or independently validated. No disclosure/report/issue was submitted.

**Next test:** a deterministic synthetic fixture with an instrumented reader that swaps the path between validation and open, plus a negative control; do not test a live third-party system.
