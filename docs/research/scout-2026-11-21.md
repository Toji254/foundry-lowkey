# Blockchain / Lowkey research scout — 2026-11-21

Checked 2026-11-21. This is an opportunity ledger, not a claim that demand or originality is proven. Public-web coverage is selective; see the report for access limits.

## Idea 1 — Authority Cutset (investigate, not build yet)

**Pitch:** Before an emergency wallet pause, show which permissions would still let a compromised actor move, approve, delegate, or upgrade assets.

**User/problem/evidence.** Wallet-security and custody operators need to know whether an “emergency stop” actually removes every authority path. Binance’s Oct. 29 incident report describes EIP-7702 delegations continuing independently of its normal withdrawal infrastructure and requiring additional on-chain revocation. Binance reported ~$6.34B affected and ~$2.85B frozen/intercepted; those are company-reported figures, not an independent loss calculation. Reuters reported on Nov. 3 and Nov. 18. This is evidence of the failure mode, not proof of customer demand for a new product.

**Small MVP (offline only):**
1. Import a JSON permission graph: wallet, actor, chain, capability, target, asset, expiry and available revoke action.
2. Model transfer/approve/delegate/upgrade paths from a compromised actor.
3. Simulate selected emergency controls; report remaining paths, candidate revocation cut-set and explicit `UNKNOWN` for unsupported permission types. No signing, live RPC or revocation transactions.

**Market/prior-art matrix**

| Product | Existing job | Overlap / verified boundary |
|---|---|---|
| [Revoke.cash](https://revoke.cash/) | Approval review/revocation; automated revoking; delegation visibility | ERC approvals and some delegation visibility are already covered; EIP-7702 revocation still depends on the wallet. |
| [Etherscan Token Approval Checker](https://etherscan.io/tokenapprovalchecker) | Inspect and revoke token/NFT approvals | Solves approval-by-approval review, not a complete authority graph. |
| [Safe modules & guards](https://help.safe.global/articles/5490514177-what-is-a-module) | Programmable execution permissions and transaction guardrails | Already covers Safe permission/control design; custom modules/guards complicate completeness. |
| [Fireblocks Governance & Policies](https://www.fireblocks.com/platforms/governance-and-policies) | Transaction policies, roles, approval workflows, DeFi/token allowance rules | Strong institutional overlap; product controls signing/workflows, but the inspected page does not document cross-layer on-chain revocation cut-set analysis. |
| [Blockaid](https://blockaid.io/transaction-security) | Transaction simulation and risk detection | Helps assess a transaction, not map and prove revocation coverage. |

**Overlap test:** token allowances = already solved; EIP-7702 delegation = wallet/revoke tools partly solve; Safe modules/guards = managed; enterprise policy engines = already strong; cross-standard emergency revocation cut-set = not found in inspected product docs (absence is not proof). Existing vendors could add this.

**Novelty:** medium-low. Graph reachability/cut-set analysis is established; the wallet permission inventory and emergency-revocation workflow are the proposed application.  
**Feasibility/risk:** moderate; graph model is easy, but custom contracts, non-standard permissions, cross-chain state and signer workflows make false “safe” results dangerous. Unsupported authority must remain `UNKNOWN`.  
**Cheap falsifier:** five synthetic wallet architectures containing allowances, EIP-7702, session permissions, Safe modules and contract roles; compare calculated residual paths against manual enumeration. If it misses one authority or merely duplicates a current wallet dashboard, kill it.  
**Potential value:** faster incident response and fewer emergency-control blind spots.  
**First user:** wallet/smart-account security engineer or custody operations lead. No interview or willingness-to-pay signal collected.  
**Verdict:** investigate further; do not build until three operator interviews and the synthetic cut-set test.

## Idea 2 — Migration Twin (investigate, low-confidence opportunity)

**Pitch:** Rehearse a CosmWasm upgrade against seeded old-version state and show which user-defined invariants changed after migration.

**Problem/user.** Contract teams can upgrade code while changing storage schemas, key names or interpretation. The official migration workflow and `cw-multi-test` support migration tests, but developers still write the scenario and assertions themselves. I found no direct customer-demand signal in this search.

**Small MVP:** old wasm + new wasm + seed script + named query/invariant set → run old code → capture query snapshots → invoke migration → run same queries → show expected/actual diff. It compares *observable/queryable state and developer-defined invariants*, not raw storage; it must never assume all values should stay identical.

**Market/prior-art matrix**

| Tool/service | Existing job | Overlap / gap |
|---|---|---|
| [cw-multi-test](https://github.com/CosmWasm/cw-multi-test) | Multi-contract test environment; migration can be exercised in tests | The migration primitive exists; the test scenario and assertions remain hand-written. |
| [CosmWasm migration tutorial](https://cosmwasm.github.io/tutorial/platform/migration) | Walks through code migration and manual testing | Covers the process, not an automated invariant snapshot/diff runner. |
| [cosmwasm-to-quint](https://github.com/informalsystems/cosmwasm-to-quint) | Semi-automated model-based tests and test generation | Adjacent test generation; not a migration-specific state-diff product. Prototype and limitations are documented. |
| [Chainscore CosmWasm verification](https://chainscorelabs.com/services/developer-tooling/formal-verification-platforms/cosmwasm-contract-correctness-verification) | Formal verification and upgrade-safety service claims | Strong service overlap, but not the proposed self-serve migration rehearsal CLI. |
| [wasmd](https://github.com/CosmWasm/wasmd) | Operational contract migration command | Performs migration operations; not an automated pre-upgrade invariant report. |

**Overlap test:** execute migration = existing; manually seed and test = existing; model-based tests = existing; automatic named-query snapshot/diff plus invariant report = not found in inspected tools, but likely an incremental packaging gap.

**Novelty:** low-medium. It wraps existing migration testing with a guided evidence workflow; no new primitive.  
**Feasibility/risk:** moderate using `cw-multi-test`; hidden storage is invisible unless a query/invariant exposes it, and snapshots can miss unmodeled state. Keep invariant declarations explicit and never claim full state coverage.  
**Cheap falsifier:** toy old/new contracts with an intentionally dropped config key, changed owner and valid migration; confirm the harness detects only declared observable invariants and does not falsely fail intentional schema changes.  
**Potential value:** less manual migration test setup, clearer release review.  
**First user:** a small CosmWasm team preparing an upgrade. No interview or pricing validation.  
**Verdict:** investigate further only if developers confirm manual migration test setup is painful.

## Idea 3 — Event Integrity CI (reject)

**Pitch:** Check that emitted EVM logs actually correspond to the contract’s state transitions and intended emitter/parameters before wallets, bridges and indexers consume them.

**Problem/evidence.** Event logs are not semantic truth; the EVM does not enforce that they match state. But this is already directly addressed by **EventSpec**, not a fresh opportunity.

**Market/prior-art matrix**

| Product/tool | Existing job | Overlap |
|---|---|---|
| [EventSpec paper](https://arxiv.org/abs/2609.07865) + [code](https://github.com/yxsec/eventspec) | Corpus-inferred event specs and differential checking; off-chain harness | Directly solves the core proposal and covers five event-semantic defect classes. |
| [Slither](https://github.com/crytic/slither) | Solidity static analysis | Some event detectors, narrower coverage. |
| Mythril / SmartCheck / Oyente | General contract analysis | Not event-semantics-first; paper’s benchmark found no direct detectors for most classes. |
| [Tenderly](https://tenderly.co/) / [Blockaid](https://blockaid.io/) | Transaction simulation/security analysis | Useful execution context, but not the same source-level event-semantic analyzer. |
| The Graph / Dune / Bitquery | Log indexing and querying | Consume logs; not source-level semantic validation. |

**Overlap test:** event collision, state-event mismatch, unauthorized emission, emission mismatch and parameter mismatch = directly covered by EventSpec. A lightweight CI wrapper would be cosmetic unless it demonstrated a real usability gap. EventSpec’s repo has no license metadata visible and uses a Docker/tool-heavy setup, so code reuse is not assumed.

**Novelty:** low.  
**Cheapest validation:** only benchmark EventSpec and current general analyzers on a synthetic event/state fixture; do not implement a competing detector.  
**Potential value:** high security importance, but existing direct prior art.  
**Verdict:** reject; no thin wrapper.

## Research leads (not additional product ideas)

- **Sui dynamic-field orphaning:** Sui docs describe the parent-deletion risk; Move Auditor already has **SUI-25** for cleanup before object deletion. The static detection idea is therefore already covered. A deployed-state monitor might differ, but no demand evidence was found. [Sui docs](https://docs.sui.io/develop/objects/dynamic-fields) · [Move Auditor SUI-25](https://github.com/pantheraudits/move-auditor/blob/main/sui-patterns.md)
- **SAEFUZZ (15 Aug 2026):** bytecode CFG/function-selector and read-write dependency guidance plus evolutionary fuzzing; paper only, no public implementation located in this search. [Paper](https://arxiv.org/abs/2608.15151)
- **SemFuzz (6 Mar 2026):** extracts semantic rules from RFCs and fuzzes protocol implementations; paper reports 10 confirmed of 16 candidates across seven implementations. No public artifact verified. [Paper](https://arxiv.org/abs/2603.05989)
- **ZK tool ecosystem:** zkFuzz and zkHydra already cover circuit fuzzing and tool orchestration. zkHydra’s Docker-first setup is heavyweight for an 8 GB laptop; treat it as research/optional backend, not a dependency. [zkFuzz](https://arxiv.org/abs/2504.11961) · [zkHydra](https://github.com/zksecurity/zkhydra)
